# ماتریس تست فاز ۱۵ — INTL Service Requests

وضعیت اجرای واقعی: **انجام‌نشده در Laravel Sandbox**. موارد زیر سناریوهای مورد انتظار برای نصب آزمایشی بعدی هستند؛ قبولی قطعی آن‌ها هنوز ادعا نمی‌شود.

| شناسه | سناریو | نتیجه مورد انتظار |
|---|---|---|
| R01 | ایجاد درخواست برای پروفایل فعال همان نمایندگی | ساخت اتمی درخواست + نسخه فرم/مدرک/Workflow و Snapshot رمزگذاری‌شده |
| R02 | مشتری غیرفعال/نمایندگی بیگانه یا خطای verifier | هیچ رکورد و گردش کاری ساخته نشود |
| R03 | ثبت دوباره با همان کلید Idempotency | همان درخواست؛ تغییر payload مردود |
| R04 | سیاست `request_management` ناقص یا وضعیت Draft ناسازگار | عدم ایجاد درخواست |
| R05 | ارسال Draft با فرم/مدرک ناقص یا verifier نامعتبر | عدم تغییر Workflow |
| R06 | ارسال موفق | تنها Workflow مرجع وضعیت؛ `first_submitted_at` یک‌بار ثبت شود |
| R07 | اجرای مستقیم Workflow بدون façade امن | رد عملیات |
| R08 | حذف نرم Draft توسط نمایندگی خودش | از فهرست/نمایش نمایندگی پنهان؛ بدون حذف فیزیکی |
| R09 | بازیابی توسط ادمین مایکروسرویس با مجوز | فقط خدمت و مشتری فعال؛ حفظ اطلاعات |
| R10 | بازیابی بدون مجوز یا برای خدمت غیرفعال | رد عملیات |
| R11 | بایگانی مشتری با درخواست فعال | رد بایگانی |
| R12 | بایگانی مشتری با Draft موجود | Draft دائماً read-only حتی بعد از بازیابی مشتری |
| R13 | تغییر پروفایل فعال | جایگزینی همه فیلدهای مشترک در Draftهای قابل‌ویرایش؛ درخواست‌های ارسال‌شده ثابت |
| R14 | لغو فوری Draft | فقط نمایندگی، انتقال معتبر به cancelled_state |
| R15 | تقاضای لغو بعد از ارسال | صرفاً نمایندگی، علت اختیاری، بدون تغییر وضعیت اصلی |
| R16 | اقدام متعارض در زمان تقاضای لغو | رد تأیید، ویرایش یا پرداخت متعارض |
| R17 | انصراف نمایندگی قبل تصمیم ادمین | وضعیت اصلی قبلی + scope اصلاح قبلی بدون تغییر |
| R18 | رد تقاضای لغو با علت اختیاری | وضعیت قبلی حفظ شود |
| R19 | تأیید تقاضای لغو فقط با تأیید ادمین | به وضعیت لغوشدهٔ مشخص خدمت وارد شود |
| R20 | رقابت انصراف/تأیید یا لغو/اقدام اصلی | دقیقاً یکی موفق؛ سابقه قابل پیگیری |
| R21 | لغو پرداخت با نتیجه نامشخص | تعیین تکلیف قبل از اقدام نهایی؛ عدم برداشت مجدد |
| R22 | درخواست اصلاح نامحدود | شماره هر دور ثبت؛ علت اصلاح اجباری |
| R23 | اصلاح محدود | فقط فیلدها و مدارک همان دور؛ direct Forms/Documents هم محدود باشند |
| R24 | ارسال مجدد اصلاح | اعتبارسنجی کامل و بستن round؛ بدون ایجاد Workflow جدید |
| R25 | انتخاب نمایندهٔ حقوقی از پروفایل یا فرم درخواست | دقیقاً یک Snapshot مستقل؛ مجوز و اعتبار توسط host بررسی شود |
| R26 | تلاش پرداخت جدید بعد از شکست قطعی | قیمت روز جدید، بدون تغییر سوابق تلاش قبلی |
| R27 | نتیجه نامشخص پرداخت یا استرداد | استعلام مرکزی؛ بدون برداشت/استرداد تکراری |
| R28 | رد یا لغو دارای سیاست استرداد | استرداد کامل صرفاً طبق سیاست پین‌شده و رویداد مورد تأیید |
| R29 | خطای ثبت Audit در تراکنش محلی | کل عملیات محلی Rollback شود |
| R30 | دسترسی نمایندگی بیگانه و جعل نقش | رد حتی با ScopeChecker اشتباه |
| R31 | دادهٔ legacy فاقد سیاست پین‌شده | fail-closed؛ نیاز به Backfill کنترل‌شده |
| R32 | تست رقابت تحت MySQL/PostgreSQL | عدم deadlock حل‌نشده، دوباره‌کاری یا تناقض وضعیت |

## روش اجرای مرحله‌ای پس از نصب

1. چک نحوی، Composer validation، `git apply --check` و صحت فایل‌ها.
2. تست هسته: `./vendor/bin/phpunit -c packages/service-requests/phpunit.xml`.
3. تست اختصاصی Sandbox: `php artisan test --filter=IntlServiceRequestsTest`.
4. سپس `php artisan test` کل Sandbox و `./vendor/bin/phpunit` کل Monorepo (باید مجموعهٔ تست‌های جدید در ریشه رجیستر شده باشد).
5. ارزیابی دستی Policy/Role/Guard، میزبان نمایندهٔ قانونی، مسیر پرداخت/استرداد mock و آزمایش رقابت روی دیتابیس واقعی مربوط به هر سازمان؛ بدون اتصال به پیشخوان عملیاتی تا دریافت مستندات معتبر.
