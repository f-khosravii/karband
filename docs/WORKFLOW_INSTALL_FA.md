# راهنمای نصب Workflow Core در INTL Platform

## خروجی و محدوده

این بسته فقط هسته عمومی، مستقل از فریم‌ورک و قابل استفاده مجدد Workflow را اضافه می‌کند. شامل `WorkflowDefinition`، `Transition`، `ActorContext`، `TransitionContext`، `StateMachine`، نتیجه تصمیم، Guard Interface، خواندن JSON، نمونه تعریف و تست‌ها است.

**این بسته پروژه NCR موجود را تغییر نمی‌دهد.** دیتابیس، پنل مدیریت، انتشار نسخه‌ها، عملیات مالی، Auth و ثبت تاریخچه باید بعداً در لایه Application/Adapter پیاده‌سازی شوند.

## نصب: فقط یکی از دو روش

**روش ZIP:** فایل `intl-workflow-core.zip` را در ریشه `intl-platform` استخراج کن. بعد از استخراج باید مسیر `intl-platform/packages/workflow/composer.json` وجود داشته باشد؛ نباید یک پوشه اضافی به نام ZIP بین این دو قرار گیرد.

**روش Git patch:** در ریشه `intl-platform` (و در شاخه کاری خودت) اجرا کن:

```bash
git apply --check /path/to/intl-workflow-core.patch
git apply /path/to/intl-workflow-core.patch
```

فایل PATCH و ZIP همان فایل‌ها را شامل می‌شوند؛ **هر دو را روی هم اعمال نکن**. پچ فقط فایل‌های جدید `packages/workflow` و `docs/WORKFLOW_INSTALL_FA.md` را می‌سازد و هیچ فایل موجودی را بازنویسی نمی‌کند.

## مرحله Composer و تست

طبق معماری فعلی، در `composer.json` ریشه باید path repository با نشانی `packages/*` وجود داشته باشد. اگر وجود ندارد، پیش از ادامه باید آن را تنظیم کنی. سپس در ریشه اجرا کن:

```bash
composer require "intl/workflow:@dev"
php packages/workflow/tests/standalone-smoke.php
./vendor/bin/phpunit -c packages/workflow/phpunit.xml
```

اگر `apps/sandbox` یک پروژه Composer مستقل است و می‌خواهی داخل آن از Workflow استفاده کنی، باید **جداگانه** path repository نسبی `../../packages/*` و require پکیج را به `apps/sandbox/composer.json` اضافه کنی. نصب ریشه الزاماً به معنای نصب در sandbox نیست.

برای اضافه‌کردن تست‌ها به مجموعه تست اصلی ریشه، داخل تگ `<testsuites>` فایل `phpunit.xml` ریشه این مورد را اضافه کن (در صورتی که مجموعه دیگری همان پوشه را از قبل اجرا نمی‌کند):

```xml
<testsuite name="Workflow">
    <directory>packages/workflow/tests</directory>
</testsuite>
```

فایل `phpunit.xml` ریشه را داخل این پچ تغییر نداده‌ایم، چون نسخه دقیق فعلی آن در اختیار ما نیست.

## معماری بازیگران

`agency`، `government_admin` و `platform_admin` نقش‌های نمونه هستند؛ هسته هیچ‌یک را در کد ثابت نکرده است. هر تعریفِ خدمت، نقش‌های مجاز هر اقدام را تعیین می‌کند. مشتری نمایندگی (`ServiceRecipient`) فقط به درخواست تجاری متصل است و از ابتدا کاربر سیستم فرض نشده است.

موتور فقط **مجوز مبتنی بر نقشِ همان انتقال** را بررسی می‌کند. تأیید اینکه ادمین به سازمان دولتی صحیح تعلق دارد، نمایندگی صاحب درخواست است، حساب احراز هویت شده است و کاربر اجازه مشاهده/ویرایش درخواست مشخصی را دارد، وظیفه اپلیکیشن میزبان است. ادمین پلتفرم به‌صورت پیش‌فرض اجازه عبور از محدودیت‌ها را ندارد.

## قرارداد تعریف و انتشار نسخه

هر تعریف شامل `id`، `version`، `initial_state`، `states` و `transitions` است. در هر انتقال `action`، `from`، `to` و `allowed_roles` اجباری، و `comment_required` و `guards` اختیاری‌اند. نسخه از عدد ۱ شروع می‌شود؛ هر خدمت می‌تواند مراحل و نقش‌های متفاوت داشته باشد.

نمونه JSON در `packages/workflow/examples/ncr-like-v1.json` برای **نمایش قابلیت** است؛ قرارداد واقعی NCR نیست و نباید بدون ممیزی وضعیت‌های عددی، دسترسی ادمین‌ها، کامل‌بودن درخواست و مسیر پرداخت در سیستم عملیاتی استفاده شود.

در آینده باید در دیتابیس تعریف‌های منتشرشده برای `(workflow_id, version)` غیرقابل‌ویرایش شوند. هر درخواست باید ID و شماره نسخه گردش کار خودش را ذخیره کند تا با انتشار نسخه جدید رفتار درخواست‌های باز عوض نشود. این هسته آماده دریافت نسخه‌ها است، ولی اجرای قواعد انتشار و ذخیره‌سازی هنوز جزو آن نیست.

## اتصال امن به یک سرویس

۱. درخواست و هویت کاربر را **از منابع معتبر سرور** بازیابی کن. مالکیت/دامنه نمایندگی یا سازمان دولتی را بررسی کن.

۲. از `workflow_id` و `workflow_version` همان درخواست، تعریف منتشرشده مطابق را بارگذاری کن. به وضعیت ارسال‌شده از کلاینت اعتماد نکن.

۳. Guardهای اعلام‌شده در تعریف را با پیاده‌سازی‌های امن همان سرویس ثبت کن. در startup یا هنگام انتشار `assertGuardsRegistered()` را صدا بزن.

۴. وضعیت فعلی درخواست را در تراکنش دیتابیس بخوان و قفل یا optimistic locking مناسب اعمال کن. `StateMachine::evaluate()` را با `TransitionContext` اجرا کن.

۵. فقط اگر نتیجه مجاز بود، وضعیت جدید را همراه با actor ID، سازمان، action، توضیح و تاریخچه **اتمیک** ثبت کن؛ سپس تراکنش را commit کن. اگر guard خطا داد، تراکنش را rollback کن. توضیح اجباری با فضای خالی پذیرفته نمی‌شود.

۶. برای پرداخت، تاییدیه را از سرویس خارجی/تراکنش معتبر بگیر و idempotency و وضعیت نامشخص را در ماژول مالی حفظ کن. Guard پرداخت صرفاً حقیقت تأییدشده را بررسی کند و هیچ تراکنش مالی مستقیمی اجرا نکند.

**نکته:** این بسته جایگزین منطق فعلی NCR نمی‌شود تا وقتی که تطابق حالت‌ها، انتقال‌ها، خطاها، تاریخچه و تأمین مالی در تست‌های یکپارچه تأیید شود.

## خطاهای قابل پیش‌بینی موتور

- `unknown_state`: وضعیت فعلی در تعریف نیست.
- `transition_not_found`: این اقدام برای وضعیت فعلی تعریف نشده.
- `actor_not_allowed`: نقش حاضر در فهرست نقش‌های مجازِ این انتقال نیست.
- `comment_required`: توضیح الزامی ثبت نشده.
- `guard_not_registered`: یک شرط تجاری ثبت نشده؛ موتور به‌صورت امن انتقال را رد می‌کند.
- `guard_rejected`: شرط ثبت‌شده انتقال را رد کرد؛ علت تکمیلی در `guardReasonCode` قرار می‌گیرد.

پیشنهاد می‌شود این کدها در لایه API به پاسخ HTTP مناسب نگاشت شوند؛ خود هسته وابستگی به HTTP ندارد.
