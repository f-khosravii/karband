# فاز ۱۴ — اصلاح Billing: قیمت روز در هر تلاش، استرداد کامل و سیاست اختصاصی خدمت

**وضعیت:** پچ اصلاحی برای نصب **در آینده** و فقط پس از پچ اصلی فاز ۸. تا پیش از تست یکپارچه روی Sandbox و دریافت مستندات معتبر API پیشخوان، هیچ عملیات مالی واقعی فعال نشود. این پچ، اصلاح فاز هشتم است؛ جایگزین اجرای آن نیست.

## ۱. حدود قطعی نیازمندی

- تمام خدمات مبلغ ثابت دارند. مرجع قیمت **Service Catalog محلی مایکروسرویس** است، نه پیشخوان؛ کد مشترک هیچ تعرفه‌ای را ثابت تعریف نمی‌کند.
- پرداخت بسته به Workflow خدمت می‌تواند قبل یا بعد از بررسی سازمان باشد؛ Billing وضعیت درخواست را تغییر نمی‌دهد.
- در آغاز **هر تلاش پرداخت**، `TrustedQuoteProvider` قیمت فعلی و مجازبودن پرداخت را از اطلاعات معتبر سرور می‌گیرد و آن قیمت برای **همان تلاش** ثابت می‌شود. پاسخ `create()` یا `retryFailed()` یا `refreshReady()` مبلغ و `revision` را برمی‌گرداند؛ UI باید مبلغ را به نمایندگی نمایش داده و پس از تأیید او، `dispatch(paymentId, confirmedAmount, confirmedCurrency, expectedRevision)` را فراخوانی کند. مبلغ فرستاده‌شده در `dispatch` فقط **تأیید قیمت ثبت‌شده** است، نه منبع قیمت‌گذاری. CSRF و ارتباط نشست معتبر در HTTP متعلق به میزبان است.
- نسخه فعلی مدت اعتبار Quote را با `quote_ttl_seconds` محدود می‌کند (پیش‌فرض ۱۵ دقیقه). قیمت تغییرکرده Service Catalog، قیمت یک تلاش تأییدنشده ولی هنوز معتبر را خودکار تغییر نمی‌دهد؛ برای Quote تازه پیش از dispatch از `refreshReady(paymentId, newKey)` استفاده کنید. API/رابط کاربری میزبان باید مبلغ جدید را دوباره نمایش دهد.
- پس از شکست **قطعی و تأییدشده بدون برداشت وجه**، `retryFailed(paymentId, newKey)` مبلغ جاری و سیاست استرداد جاری را می‌خواند و تلاش مستقل جدید ایجاد می‌کند. مبلغ و شناسه خارجی تلاش قبلی در `intl_payment_attempts` تغییر نمی‌کنند. ارسال مجدد `newKey` همان تلاش جاری را برمی‌گرداند، نه تلاش دیگری.
- در وضعیت `processing`، `pending` یا `unknown` فقط `reconcile()` با کلید خارجی **قبلی** مجاز است؛ هیچ تلاش جدیدی ساخته نمی‌شود. Timeout/5xx/«پیدا نشد» مبهم، شکست قطعی نیست.
- مقدار مبلغ integer و واحد `currency` سه‌حرفی است؛ **واحد واقعی API پیشخوان (ریال/تومان و نحوه نمایش)** قبل از اتصال واقعی باید از قرارداد رسمی تأیید شود. هیچ تبدیل حدسی مجاز نیست.

## ۲. سیاست استرداد — فقط تمام مبلغ یا هیچ

- میزبان باید `TrustedRefundPolicyProvider` را با **سیاست معتبر و قابل اعتماد همان خدمت** متصل کند؛ تنظیمات سیاست در این پچ به جدول کاتالوگ تحمیل نمی‌شود. اتصال typed Service Catalog جزو پچ هماهنگ‌سازی بعدی است.
- سیاست از نگاشت `eventCode => initiationMode` ساخته می‌شود. عدم وجود رویداد یعنی **استرداد مجاز نیست**. شیوه هر رویداد: `automatic`، `admin_approval` یا `manual`؛ بنابراین یک خدمت می‌تواند برای رد و لغو رفتار متفاوتی داشته باشد.
- سیاست هنگام ساخت هر تلاش پرداخت ذخیره می‌شود. برای پرداخت موفق، سیاستِ همان تلاش موفق در تمام عمر درخواست ملاک است؛ تغییر آینده تنظیمات خدمت روی سوابق گذشته اعمال نمی‌شود. `RefundPolicy::nonRefundable()` برای خدمت غیرقابل‌استرداد باید به‌صورت **صریح** برگردانده شود؛ نبود Binding به معنی غیرقابل‌استرداد نیست و باعث خطا می‌شود.
- فقط پرداخت `succeeded` همراه با مرجع تأییدشده مرکزی قابل استرداد است. مقدار استرداد **دقیقاً مبلغ ثبت‌شده پرداخت موفق** است؛ امکان تعیین مبلغ کمتر یا مبلغ توسط درخواست کاربر وجود ندارد.
- ثبت رویداد قابل استرداد باید از **مسیری مورد اعتماد میزبان** بیاید و `TrustedRefundEventVerifier` وقوع واقعی آن رویداد و تعلق آن به درخواست را تأیید کند. کنترل `billing.refund.propose` هم الزامی است. هیچ Route/Controller عمومی برای event code ارائه نشده است.
- `automatic`: `propose()` وضعیت `ready` ایجاد می‌کند؛ Worker مجاز با Permission مستقل باید `dispatch()` را فراخوانی کند. این پکیج به‌تنهایی Worker و ارسال خودکار پس‌زمینه راه نمی‌اندازد.
- `admin_approval`: `propose()` در وضعیت `awaiting_approval` باقی می‌ماند؛ تنها `government_admin` با Permission مشخص می‌تواند `approve()` یا `reject()` کند؛ پس از تأیید، Worker مجاز `dispatch()` می‌کند.
- `manual`: تنها پرونده `manual_pending` محلی ایجاد می‌شود. **هیچ فراخوانی خودکاری به پیشخوان و هیچ متد ثبتِ موفقیتِ دستیِ تأییدنشده وجود ندارد**. برای تکمیل این مسیر، Adapter استعلام/مدرک معتبر پیشخوان نیاز است؛ تا آن زمان به «انجام شد» تغییر نمی‌کند.
- `dispatch()` پیش از تماس شبکه، وضعیت `processing` را در دیتابیس Commit می‌کند. Crash و نتیجه مبهم فقط با `lookup` همان کلید اصلاح می‌شود. در این نسخه برای هر پرداخت حداکثر **یک پرونده استرداد** مجاز است؛ پس از رد اداری یا شکست قطعیِ استرداد، پرونده دوم خودکار ساخته نمی‌شود و رسیدگی بعدی نیازمند طراحی و ممیزی مستقل است.
- ادعای «ضدبرداشت/استرداد تکراری قطعی» **بدون تعهد رسمی پیشخوان به Idempotency و Lookup پایدار قابل ارائه نیست**. تا آن زمان فقط Fake Gateway برای Sandbox مجاز است.

## ۳. مرزهای پکیج و پایگاه داده

- `intl/billing` هسته مستقل: RefundPolicy، RefundCommand، RefundOutcome و StateMachine.
- `intl/billing-laravel` مدیریت تراکنش محلی، تلاش‌های قیمت‌گذاری‌شده و پرونده‌های استرداد؛ `CentralPaymentGateway` قبلی برای پرداخت و `CentralRefundGateway` **جداگانه** برای استرداد.
- هر مایکروسرویس دیتابیس خودش را دارد؛ پیشخوان سیستم بیرونیِ مشترک برای **پرداخت** است. مایکروسرویس نه کیف پول دارد، نه Balance/Wallet ID را مدیریت می‌کند.
- Migration افزایشی این فاز: `intl_payment_attempts`، `intl_full_refunds` و `intl_refund_events`. رکوردهای قبلی (اگر فاز ۸ قبلاً مهاجرت کرده باشد) فقط با `policy_verified=false` Backfill می‌شوند؛ **استرداد رکورد قدیمی بدون تعیین مستقل سیاست تاریخی ممنوع**. اگر فاز ۸ قبلاً با تلاش‌های متعدد اجرا شده باشد، قیمت تلاش‌های قدیمی از داده‌های v1 قابل بازسازی قطعی نیست؛ قبل از Migration داده واقعی، ممیزی جداگانه اجباری است. از به‌روزرسانی ساختگی Policy قدیمی خودداری کنید.
- برای حفظ امنیت، پکیج هیچ مجوز Spatie را خودکار نمی‌سازد/اعطا نمی‌کند، هیچ API پیشخوان را حدس نمی‌زند و بدون ثبت صریح `TrustedQuoteProvider`، `TrustedRefundPolicyProvider` و `TrustedRefundEventVerifier` fail-closed است.
- ثبت رویدادهای Billing در جدول خودش مکمل Audit است. اتصال به `intl/audit-laravel` و سیاست نگهداری رویدادها، نظارت بر `unknown`های قدیمی و Job زمان‌بندی‌شده در فاز یکپارچه‌سازی تکمیل می‌شود.

## ۴. ترتیب نصب آینده (فعلاً اجرا نکنید)

۱. روی Branch آزمایشی و با Snapshot معتبر، ابتدا **پچ اصلی فاز ۸** و پیش‌نیازها نصب شوند. اگر Phase 8 قبلاً اعمال شده، **فقط پچ اصلاحی فاز ۱۴** را اضافه کنید؛ ZIP و Patch یک فاز را هم‌زمان اعمال نکنید.

```bash
cd ~/Desktop/intl-platform
git apply --check intl-phase14-billing-corrections.patch
git apply intl-phase14-billing-corrections.patch
composer require 'intl/billing:dev-main' -W
./vendor/bin/phpunit -c packages/billing/phpunit.xml
cd apps/sandbox
composer require 'intl/billing:dev-main' 'intl/billing-laravel:dev-main' -W
php artisan migrate:status
php artisan test --filter=IntlBillingTest
php artisan test
```

۲. **Migration فقط در دیتابیس Sandbox**؛ ابتدا نسخه Schema، وضعیت پکیج قبلی و Connectionهای محلی را بررسی کنید. در production بدون Plan/backup و تست روی DB مقصد، هیچ Migration یا استرداد/پرداخت اجرا نشود. این پچ برای داده عملیاتی منتقل‌شده از نسخه قبلی مستلزم بررسی جداگانه است.

۳. پچ Phase 12 Reference Host و Service Requests فعلی ممکن است برای متد جدید `dispatch` یا Binding جدید Policy نیاز به ارتقا داشته باشند؛ اتصالِ آن‌ها به فاز ۱۵/۱۶ موکول است. تا تکمیل آن‌ها نباید پوشش end-to-end ادعا شود.

## ۵. موارد باقی‌مانده قبل از عملیاتی‌شدن

- قرارداد واقعی API پیشخوان: refund endpoint/semantics، lookup پرداخت و استرداد، نهایی‌بودن `failed`، Idempotency، نرخ/واحد، TLS/credential، محدودیت زمانی و خطاها.
- سیاست typed هر خدمت در Service Catalog + Snapshot معتبر هنگام ایجاد هر تلاش؛ رابط نمایش و تأیید قیمت به نمایندگی؛ Backend قابل اعتماد برای رویدادهای مجاز؛ مجوزها و Scope واقعی.
- پیاده‌سازی Manual refund attestation، Worker reconciliation و هشدار برای outcome نامشخص، ذخیره لاگ گزینشی و Audit، تست MySQL/PostgreSQL هم‌زمانی، سناریوهای رد و لغو پیش/پس از پرداخت.
- تأیید رسمی سیاست قانونی استرداد هر سازمان و دوره نگهداری سوابق؛ هیچ‌کدام در هسته عمومی فرض نشده‌اند.
