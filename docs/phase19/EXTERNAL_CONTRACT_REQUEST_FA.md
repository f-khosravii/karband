# پرسش‌نامه رسمی اتصال‌های بیرونی — قبل از هر عملیات مالی واقعی

## ۱. پرسش‌های لازم از تیم پیشخوان مرکزی

- محیط Sandbox رسمی، URLها، راهکار احراز هویت، TLS، محیط/سازمان و نحوه امن نگهداری Credential چیست؟ Credentialها نباید در پچ، گیت یا لاگ قرار گیرند.
- واحد مبلغ دقیقاً چیست (ریال، تومان یا واحد دیگر)؟ قوانین integer، حداکثر مبلغ و precision چیست؟
- `requestKey` سراسری از چند مایکروسرویس چگونه Namespace می‌شود؟ ضمانت Idempotency چه مدت برقرار است؟ اگر همان کلید با مبلغ متفاوت ارسال شود پاسخ چیست؟
- تفاوت پاسخ «شکست قطعی بدون برداشت»، «نامعلوم»، «در انتظار» و «موفق قطعی» چیست؟ وضعیت `404/not found` بعد از Timeout دقیقاً چه معنایی دارد؟
- API استعلام پرداخت با **همان کلید اولیه** چیست و چه مدت سابقه را نگه می‌دارد؟ ضمانت شناسه مرجع پرداخت و صحت پاسخ چیست؟
- آیا API برای **استرداد کامل** (نه جزئی) وجود دارد؟ آیا کلید یکتا، ارجاع به پرداخت اصلی، تضمین No-Refund شکست قطعی و استعلام نتیجه استرداد ارائه می‌شود؟
- برای رسیدگی دستی، مدرک قابل استعلام و معتبر اتمام استرداد چگونه تولید/تأیید می‌شود؟
- محدودیت Rate، Retry-After، Timeout، قطعی طولانی، تسویه ناسازگار و روند پشتیبانی عملیاتی چیست؟

**تا پاسخ مستند و Contract Test روی Sandbox رسمی، Gateway واقعی و Worker خودکار نباید فعال شوند.**

## ۲. پرسش‌های لازم از هر سازمان برای احراز اختیار نماینده حقوقی

- نوع مدارک، سامانه استعلام و نحوه تشخیص شخص حقوقی/نماینده چیست؟ از بین دستی، خارجی، ترکیبی کدام روش انتخاب شده است؟
- آیا تأیید قبلی برای درخواست جدید قابل استفاده است؟ تاریخ انقضا، ابطال و ارتباط مستندات با درخواست کجاست؟
- هنگام قطعی سامانه خارجی، انتظار یا بررسی دستی جایگزین؟ چه مجوز مشخصی به ادمین داده می‌شود و شواهد تصمیم کجا ثبت می‌شوند؟
- آیا نتیجه استعلام دارای امضا/شناسه پاسخ/زمان و سیاست نگهداری داده است؟ پاسخ مبهم و Timeout نباید به تأیید تبدیل شوند.

## ۳. معیار تست جداگانه

بدون راه‌اندازی Production، برای مسیرهای «رد/لغو پس از پرداخت»، «استعلام نتیجه مبهم»، «ابطال تأیید قبلی» و «Fallback دستی با مجوز» تست قراردادی با داده ساختگی و ثبت شواهد قابل ارائه ضروری است.
